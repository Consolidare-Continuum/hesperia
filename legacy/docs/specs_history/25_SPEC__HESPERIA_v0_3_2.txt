0. GOAL OF v0.3.2
============================================================

v0.3.2 turns “v0.3 math” into an operationally testable, minimal runtime:

A) Deterministic measurement core:
- text → (dominant Area, dominant Family)
- region-building (seed → traversal)

B) Guard discipline:
- Σ (static invariants) is non-bypassable

D) Output contracts are stable (for wiring into external systems / LLM wrappers):
- a small “6-key operational summary” exists for fast integration,
  and a larger “full summary” remains available for deeper RAG.

2. CANONICAL OUTPUT CONTRACTS
============================================================

2.1 Minimal operational summary (required for v0.3.2 runtime)
------------------------------------------------------------
This is the “tight” contract used by upstream apps and tests.

JSON (success) MUST be exactly 6 keys:

{
  "dominant_area": <int 0..11>,
  "dominant_family": <int 0..287>,
  "governance": <float 0..1>,
  "loopability": <float 0..1>,
  "tension_energy": <float >=0>,
  "obstacle_score": <float >=0>
}

Rules:
- No extra keys. No lists. No debug payloads.
- All floats must be finite (no NaN/Inf).
- Values must be deterministic for the same raw_text and same config.

2.2 Minimal error summary (required)
-----------------------------------
JSON (error) MUST be exactly 3 keys:

{
  "error": true,
  "message": "<string>",
  "code": <int http-like status>
}

2.3 Full summary (optional in v0.3.2, but aligned with 14_SPEC)
--------------------------------------------------------------
When available, it may include region sides, supporting statements, and explanations.
But the minimal operational summary above must always exist (even if full summary is disabled).


============================================================
3. v0.3.2 PIPELINE (NORMATIVE)
============================================================

Given raw_text text X:

Step 0 — Normalize
- stable whitespace normalization
- stable tokenization (deterministic)
- length cap (default: 10_000 chars; configurable)

Step 1 — Attribution (deterministic)
- words → Families/Areas using Dictionary A (core) and Dictionary B (surface/frozen)
- sentence/statement aggregation is allowed but must not introduce stochasticity

Step 2 — Region seed
- derive initial seed sides (sideId set) from dominant Family/Area
- seed weights (tau) must be deterministic

Step 3 — Traversal loop (base plane)
- run loop/traversal policy from 40_POLICY and math from 21_MATH
- compute loopability, tensionEnergy, obstacleScore

Step 4 — Guards
- Σ: enforce frozen constants, index bounds, normalized metric bounds
- Γ: enforce bounded penalties and bounded step factors
- Θ: compute governance score and gate outcome (allow / require_correction / forbid)
  NOTE: v0.3.2 runtime exports only governance score in minimal summary;
        allow/forbid flags belong to full summary.

Step 5 — Shadow layer (conditional)
- Shadow activates when risk R crosses thresholds (24_SPEC v1.0).
- Shadow provides:
  - constrained candidate set C
  - shadow-adjusted scores
  - failure codes (logged)
- Shadow must never violate Σ invariants.
- Shadow is permitted to select a different next step than base plane
  ONLY within the candidate set C and only one-step-ahead at a time.

Step 6 — Output
- Always return minimal operational summary (2.1) or error summary (2.2).


============================================================
4. SHADOW LAYER v1.0 INTEGRATION REQUIREMENTS (v0.3.2)
============================================================

Shadow layer is not “poetry”; it must be measurable.

4.1 Inputs (per step)
- current_family (0..287)
- governance, loopability (0..1)
- tension_energy, obstacle_score (>=0)
- previous risk (state.r_prev)
- neighborhood function n_base(F)  -> base neighbors
- mirror function φ(F)            -> involutive mapping

4.2 Candidate set (must match 24_SPEC)
- mirror = φ(F)
- N_shadow(F) = N_base(F) ∩ N_base(mirror)
- C = N_shadow(F) ∪ {mirror}

4.3 Mass decay and penalties
- shadow_mass(k) = max(m_min, (1 - sinkage) * exp(-λ*k))
- shadow-adjusted:
  - governance_hat = governance * mass
  - loopability_hat = loopability * sqrt(mass)
  - tension_hat = tension * (1 + α*(1-mass))
  - obstacle_hat = obstacle * (1 + β*(1-mass))

4.4 Θ abuse detection (required)
- shadow_time_ratio threshold + enter_count threshold triggers abort
- abort produces SHADOW_ABORT_ABUSE failure code, logged

4.5 What must be logged (minimum)
- shadow_active (0/1)
- shadow_hop_count
- shadow_time_ratio
- shadow_mass
- failure_code (if any)


============================================================
5. GUARD DISCIPLINE (v0.3.2)
============================================================

v0.3.2 requires a “no bypass” rule:
- There must not exist any API path that returns the minimal summary without Σ enforcement.

Minimum invariants:
- all constants frozen and consistent
- all IDs within ranges
- governance ∈ [0,1]
- loopability ∈ [0,1]
- tension_energy >= 0 (finite)
- obstacle_score >= 0 (finite)

Bounds:
- Any penalty term must be clamped to [0,1] when defined as a normalized penalty.
- Any factor derived from length/hops/time must be clamped so it cannot explode.

Configuration:
- v0.3.2 runtime must load a versioned external config file, e.g.:
  guard_config_v1.json
with defaults that match the specs.
