////////////////////////////////////////////////////////////
0. WHAT HESPERIA IS (AND ISN’T)
////////////////////////////////////////////////////////////

HESPERIA is a deterministic semantic substrate wrapped around LLMs.
It is a geometry + data + metrics engine that stabilizes meaning and 
exposes clear, numeric signals an LLM can respect.

At its core, HESPERIA does four things:

1. **Fix the geometry of meaning.**  
   - 12 Areas on a semantic ring (#AREAS).  
   - 24 Families per Area (#FAMILIES_PER_AREA).  
   - 250 hexes per Family (#HEXES_PER_FAMILY).  
   - 6 sides per hex (#SIDES_PER_HEX).  
   - 432,000 atomic truth sides (#TOTAL_SIDES).  
   Each side is an addressable “truth slot” identified by `sideId`.

2. **Deterministically classify text into that geometry.**  
   - A 5‑stage attribution engine maps words → Families/Areas using
     dictionary, nearest neighbors, centroids, polarity axes, and
     context overrides.  
   - Sentences and statements get structured attributions
     (#F_sentence, #A_sentence, #F_statement, #A_statement,
     inward/outward vectors).

3. **Store and retrieve content as a geometric region.**  
   - Each statement is placed on one side (with #tau truth weight) and
     persisted in SQL + vector DB.  
   - Queries retrieve statements from the same semantic shard and
     reconstruct a Region R of sides for reasoning.

4. **Compute metrics and governance signals.**  
   - Structural metrics (T(R), C(R), X_A, X_F, fragIndex, entropy).  
   - Loopability, coveragePhi, tensionEnergy, O_obstacle.  
   - EvidenceQuality, temporalStability, decisionIntegrity, strategicScore.  
   - Final governance decision: allow / require_correction / forbid.

The **system**, in this blueprint, is the CLI execution_flow:
user raw_text → HESPERIA core → `HESPERIAResult`.  
Any external LLM (e.g. OpenAI assistant) is a *consumer* of that summary,
not part of the system itself.


============================================================
1. GEOMETRY AND COORDINATES (SUMMARY)
============================================================

HESPERIA uses a hex‑sphere lattice as a fixed semantic skeleton.

1.1 Constants (see VARIABLES.md)
--------------------------------

- `AREAS = 12`  
- `FAMILIES_PER_AREA = 24`  
- `HEXES_PER_FAMILY = 250`  
- `SIDES_PER_HEX = 6`  
- `TOTAL_FAMILIES = AREAS * FAMILIES_PER_AREA = 288`  
- `TOTAL_HEXES = TOTAL_FAMILIES * HEXES_PER_FAMILY = 72,000`  
- `TOTAL_SIDES = TOTAL_HEXES * SIDES_PER_HEX = 432,000`

These constants are *frozen*. Changing them means defining a new
version of HESPERIA.


1.2 Coordinates
---------------

Every side is addressed by:

- `area`        ∈ [0..11]  
- `familyLocal` ∈ [0..23] (within Area)  
- `hexIndex`    ∈ [0..249]  
- `sideIndex`   ∈ [0..5]

From these we derive:

- `familyGlobal = area * FAMILIES_PER_AREA + familyLocal`  
- `sideId` (0..TOTAL_SIDES-1), as defined in 13_SPEC__Indexing...:

```java
int sideId = (((familyGlobal * HEXES_PER_FAMILY) + hexIndex)
              * SIDES_PER_HEX) + sideIndex;
```

This `sideId` is the canonical index for:
- `tau[sideId]` (truth),
- `areaOf[sideId]`,
- `familyOf[sideId]`,
- SQL `side.side_id`,
- vector DB annotations (optional).


1.3 Human labels
----------------

Humans can refer to coordinates as:

```text
A03-F05-H120-S3
```

meaning:
- Area 3, Family 5 (local), Hex 120, Side 3.  
The formal definition is in 13_SPEC__Indexing_and_Coordinates_v1_0.txt.

2. ONTOLOGY: AREAS, FAMILIES, RING
============================================================

HESPERIA’s ontology is defined in the family docs:

- `30_FAMILIES__HESPERIA_hex_canonical_v1_0.txt`  
- `31_FAMILIES__area_family_table_full.txt` (canonical table)  
- `32_FAMILIES__concise_spec_v2_1.txt`

Each Area has a name (GOOD, HARM, TRUTH, DECEIT, etc.) and 24 canonical
Families. The Areas are arranged on a ring with antipodal pairs and a
fixed traversal order.

Best practices:
- Treat Areas and Families as *stable coordinates*, not tuning knobs.
- If ontology evolves, version the family files and preserve mappings.

3. SEMANTIC ATTRIBUTION ENGINE (WORD → STATEMENT)
============================================================

The attribution engine is specified in detail in
12_SPEC__Semantic_Engine_v0_4.txt. This section gives the high‑level
intent and best‑practice notes.


3.1 Word-level attribution
--------------------------

Goal: map any lemma into a Family/Area deterministically.

Stages:
1. **Dictionary match** using `dictWordToFamily`.  
   - If present, use this Family and stop.
2. **Nearest neighbors in `words` collection (vector DB)** using `embedWord`.  
   - Vote over neighbors with similarity ≥ `THRESH_NN`.  
3. **Family centroid similarity** using `embedFamily`.  
   - Pick the Family with highest cosine if neighbors are ambiguous.  
4. **Axis polarity correction** using `axisPos/axisNeg`.  
   - Project onto 6 bipolar axes, adjust Area if polarity contradicts.  
5. **Phrase/sentence overrides.**  
   - After context is known, override misclassified words where allowed.

Best practices:
- Keep dictionary curated and conservative.  
- Version the embeddings and thresholds (`THRESH_*`) explicitly.  
- Log difficult words (unstable classifications) for ontology review.


3.2 Sentence and statement attribution
--------------------------------------

Sentence:
- Aggregate word families/areas into `F_sentence[288]` and `A_sentence[12]`.  
- Normalize and pick dominantFamily/dominantArea.

Statement (3–5 sentences):
- Aggregate `F_sentence` → `F_statement`; `A_sentence` → `A_statement`.  
- Embed the whole statement (`E_statement`).  
- Correct using centroids and polarity axes.  
- Compute inward/outward vectors with `familyInward` and `familyOutward`.

Output: a `StatementAttribution` with:
- Family/Area,  
- `F_statement`, `A_statement`,  
- `inwardVector[12]`, `outwardVector[12]`.


3.3 Forward and backward evolution
----------------------------------

Forward:
- text → words → sentences → statement → placement on side → Region R.

Backward:
- Compare per‑word Family to statement Family.  
- If allowed by inward semantics, update dictionary.  
- Else, record outward reference.

Best practices:
- Only allow backward corrections under explicit policies (see 41_POLICY).  
- Log all backward changes with rationale and `trace(R)` entries.

4. DATA MODEL: SQL + VECTOR DB
============================================================

The data model is fully detailed in 15_SPEC__Data_and_Schema_v0_1.txt.
Here we summarize the essentials.


4.1 SQL schema (core)
---------------------

Key tables:

- `area(id, name, ring_index)`  
- `family(id, area_id, local_index, name)`  
- `hex(id, family_id, hex_index)`  
- `side(side_id, area_id, family_id, hex_index, side_index, tau, statement_id, last_updated)`  
- `statement(id, raw_text, area_id, family_id, inward_vector, outward_vector, f_vector, a_vector)`  
- `dictionary_word(lemma, family_id, area_id, source, updated_at)`  
- optional `side_provenance`, `domain_profile`.

Best practices:
- Always store full coordinates in `side`.  
- Enforce referential integrity: `family.area_id` must match `area.id`.  
- Use `side_id` as the single primary key for sides.


4.2 Vector DB collections
-------------------------

Collections:
- `words(lemma, family_id, area_id, embedding)`  
- `statements(statement_id, family_id, area_id, side_id?, embedding)`  
- `families(family_id, area_id, embedding)`  
- `areas(area_id, embedding)`

Best practices:
- Mirror IDs exactly between SQL and vector DB.  
- Always filter statement searches by `family_id` and `area_id` where possible.  
- Keep embedding dimensionality and model choice documented.

5. INGESTION PIPELINE (DB-CENTRIC)
============================================================

This section explains how to store new content into HESPERIA from the
DB point of view. It assumes the semantic engine already produced a
`StatementAttribution` and an embedding.


5.1 Steps for a new statement
-----------------------------

Given:
- `text` (raw string),
- `StatementAttribution` (family, area, vectors),
- `E_statement` (embedding),
- possibly book/author metadata.

1) Insert statement row in SQL  
   - Create a `statement` record with text, `area_id`, `family_id`,
     inward/outward vectors, and optional F/A vectors.

2) Insert statement embedding in vector DB  
   - Upsert into `statements` collection keyed by `statement_id`.

3) Assign side and update tau  
   - Use GeometryService + indexing spec to pick a `side_id` and full
     coordinate (area, family, hexIndex, sideIndex).  
   - Upsert into `side` table with tau and `statement_id`.

4) Optional: update provenance  
   - Insert or update `side_provenance` with credibility/recency/consensus.

Best practices:
- Keep ingestion idempotent by using UPSERT patterns on `side` and dictionary.  
- Separate ingestion logs from user‑facing logs; ingestion errors should
  never block query behavior for existing data.


5.2 Dictionary updates
----------------------

When backward evolution approves a lemma correction:
- Upsert `dictionary_word(lemma, family_id, area_id, source)` in SQL.  
- Optionally upsert the lemma’s embedding into `words`.

Best practices:
- Treat dictionary changes as “schema‑like”: review and track them.  
- Include `source` to distinguish curated vs learned entries.

6. QUERY PIPELINE (SYSTEM VIEW)
============================================================

The query execution_flow is the core of the HESPERIA system:
raw_text text → `HESPERIAResult`.

High‑level stages:
1. Attribution.  
2. Sharded retrieval.  
3. Region construction.  
4. Traversal and metrics.  
5. Governance decision.  
6. `HESPERIAResult` assembly.


6.1 Attribution
----------------

- Receive `input_text`.  
- Run AttributionService:
  - classify words → sentences → statement;  
  - obtain `StatementAttribution` and `E_statement`.

Output:
- dominant `area_id`, `family_id`,  
- distributions and inward/outward vectors.


6.2 Sharded retrieval (vector DB + SQL)
---------------------------------------

1) Vector DB search in `statements` collection:
   - embedding: `E_statement`,  
   - filter: `{ family_id, area_id }`,  
   - top‑K results.

2) Load `statement` rows for these IDs from SQL.  
3) Load `side` rows where `statement_id` is in this set.

Output:
- a list of sides with full coordinates and `tau`,  
- a list of supporting statements with text and metadata.


6.3 Region construction
-----------------------

GeometryService:
- Build a `Region R` from the retrieved sides.  
- Optionally merge with the seed side for the current raw_text statement.

Output:
- `Region R` containing relevant sides and statements.


6.4 Traversal and metrics
-------------------------

TraversalService:
- Run loop‑based traversal over R along the Area ring, guided by:
  - `A_vec`, `F_vec`,  
  - family and area dominance,  
  - novelty and obstacle heuristics.  
- Compute:
  - `loopability`,  
  - `coveragePhi`,  
  - `tensionEnergy`,  
  - `O_obstacle`,  
  - structural metrics: `T(R)`, `C(R)`, `fragIndex`, `X_A`, `X_F`,
    `areaEntropy`, `adjacencyCorrelation`,
  - temporal and evidence metrics where available.

Best practices:
- Implement traversal as a pure function of `Region` and config.  
- Avoid hidden state inside traversal; expose all decisions via metrics.


6.5 Governance and `HESPERIAResult`
-----------------------------------

Governance layer:
- Combine metrics into:
  - `decisionIntegrity`,  
  - `strategicScore`,  
  - governance flags: `allow`, `require_correction`, `forbid`.
- Generate a short `explanation` string referencing specific metrics.

Summary assembly:
- Build a `HESPERIAResult` object as defined in
  14_SPEC__Services_and_APIs_v0_1.txt:
  - `input_text`, `statement_id?`,  
  - `area_id`, `family_id`,  
  - metrics, governance,  
  - `sides[]` (coordinates, tau),  
  - `supporting_statements[]` (with optional book/author),  
  - `explanation`, `log_id?`.

Best practices:
- Always produce a `HESPERIAResult` even if retrieval is weak; let
  governance and metrics express uncertainty.
- Persist or at least hash the summary for audit when possible.


============================================================
7. EXTERNAL LLM WRAPPERS (OUTSIDE SYSTEM)
============================================================

HESPERIA does **not** prescribe LLM prompts or user interfaces. It only
emits structured outputs that an LLM can reason about.

External LLM wrappers should:
- Accept a `HESPERIAResult`.  
- Respect governance flags:
  - If `forbid == true`, refuse or escalate.  
  - If `require_correction == true`, ask for clarification or adjust
    the answer carefully.  
  - If `allow == true`, proceed while still using metrics as context.
- Use `supporting_statements` and `sides` to:
  - explain reasoning,
  - show relevant book/author fragments,
  - justify or contest user raw_text.

Best practices:
- Treat HESPERIA’s metrics as *constraints* on LLM behavior, not
  suggestions.  
- Keep LLM prompts declarative: “You must respect allow/forbid, and you
  must mention obstacle/tension when they are high.”


============================================================
8. LOGGING, OBSERVABILITY, AND EXPERIMENTATION
============================================================

For serious use, HESPERIA must be observable.

Recommended logs per query:
- Raw_text text hash or ID.  
- `statement_id` and main attribution (area/family).  
- Key metrics: `loopability`, `coveragePhi`, `tensionEnergy`,
  `O_obstacle`, `decisionIntegrity`, `strategicScore`.  
- Governance decision and explanation.  
- IDs of main supporting statements and sides.

Experimentation knobs:
- Thresholds (`THRESH_*`, tau thresholds, obstacle thresholds).  
- Retrieval K and shard filters.  
- Governance cutoff values.

Best practices:
- Log enough to replay decisions, but avoid storing raw sensitive text
  where not needed.  
- Use offline replay to test new thresholds/policies on historical
  queries.

10. ROLES AND RESPONSIBILITIES
============================================================

Summarizing role mapping (see also AGENTS.md and 14_SPEC):

- **Backend / Systems Engineers**  
  - Own services, repositories, and pipelines.  
  - Ensure DB and vector DB interactions respect indexing and schema.  
  - Implement `HESPERIAResult` emission and logging.

- **ML / NLP Engineers**  
  - Own embeddings, vector DB config, thresholds, and attribution quality.  
  - Tune retrieval and attribution accuracy while preserving determinism.

- **Ontology / Knowledge Engineers**  
  - Own Areas/Families definitions and dictionary entries.  
  - Curate edge cases and interpret logs of misclassifications.

- **Safety / Governance Engineers**  
  - Own obstacle thresholds, tension limits, governance decision rules.  
  - Define how LLMs must react to HESPERIA metrics.


============================================================
11. VERSIONING AND CHANGE POLICY
============================================================

- **Geometry constants and indexing** (AREAS, FAMILIES_PER_AREA, etc.)
  are frozen within a major HESPERIA version. Changes require:
  - new indexing spec version,  
  - new blueprint version,  
  - clear migration path.

- **Semantic engine behavior**, thresholds, and ontology can evolve,
  but changes must be:
  - documented in 12_SPEC and/or family docs,  
  - reflected in VARIABLES.md and ACADEMIC.md if they add new variables.

- **DB schema and vector layout** (15_SPEC) must stay aligned with
  services and pipelines in this blueprint.
